<objective>
Activate the pipeline built in plans 01-03 and 01-05: run the CI workflow against the real
repository, observe the exact status-check context it reports, enable branch protection on `main`
requiring that check, and link the Vercel project so a production deployment exists at a public URL.

Purpose: 01-RESEARCH.md Pitfall 4 and Open Question 1 both establish that the required status-check
context string cannot be known in advance — GitHub may report it as `ci` or as `CI / ci` depending
on workflow structure, and a mismatched context returns HTTP 200 while leaving PRs permanently
blocked on a check that never resolves. The only safe sequence is: run the workflow, read the actual
name, then set protection. This plan enforces that ordering.

Output: a green CI run on `main`, branch protection configured with the observed context, and a live
Vercel production deployment whose URL is recorded in the summary for plan 01-07 to verify against.

This plan modifies no repository files. It changes GitHub and Vercel platform state.
</objective>

    Enable branch protection on `main` for `devKiNGCRiC/PinchPop`, requiring the CI status check
    observed in Task 1, per D-08.

    Call the "Update branch protection" REST endpoint:
    `gh api --method PUT -H "Accept: application/vnd.github+json" -H "X-GitHub-Api-Version: 2022-11-28" repos/devKiNGCRiC/PinchPop/branches/main/protection`.

    The endpoint requires every top-level field to be present, including the nulls. Supply:
    `required_status_checks` with `strict: true` and a `checks` array containing one entry whose
    `context` is the exact string from Task 1 and whose `app_id` is `-1` (meaning any app, including
    GitHub Actions, may satisfy the check); `enforce_admins: false`;
    `required_pull_request_reviews: null`; and `restrictions: null`.

    Prefer passing a JSON body via `--input` (piping a heredoc of the full object into
    `gh api ... --input -`) over the `-f`/`-F` bracket-array flag syntax shown in 01-RESEARCH.md's
    Code Examples — nested-array flags are error-prone to quote correctly and the JSON body is
    unambiguous. The 01-RESEARCH.md flag form remains valid as a fallback if `--input` is unavailable.

    Per Assumption A4, if the API returns HTTP 422 rejecting the `checks` array shape, retry with the
    older equivalent: `required_status_checks` with `strict: true` and
    `contexts: ["<observed context>"]`. Both forms were confirmed present in the same doc fetch; the
    `checks` form is merely the currently preferred one.

    `enforce_admins` MUST stay `false`. 01-RESEARCH.md's Security Domain records this as deliberate
    scope-matching for D-07/D-08 (require the CI check, nothing more), and it has a practical
    consequence this project depends on: with `branching_strategy: none`, subsequent GSD phases commit
    and push directly to `main`, and admin bypass is what keeps that workflow functional. Tightening
    to admin-inclusive enforcement is a deliberate one-line follow-up for a later phase, not a Phase 1
    requirement — do not do it here.

    Per D-07, require ONLY the CI check. Do NOT add Vercel's deployment status as a required check and
    do NOT configure Vercel to wait on the CI check — the two pipelines run independently by design.

    Do NOT enable `required_pull_request_reviews`, `required_linear_history`, `required_signatures`,
    or `allow_force_pushes: false` beyond the endpoint's defaults — none of those are in D-08's scope,
    and a solo-developer repository requiring PR reviews would block its own author.

    After the call, read the protection state back and confirm the stored context matches the
    observed check name exactly, character for character. A 200 response alone does not prove the
    context matches anything real — that is exactly Pitfall 4's trap.
  </action>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Local machine → GitHub API | The `gh` CLI mutates repository protection settings with the developer's credentials |
| GitHub repository → Vercel build environment | Vercel's GitHub App gains read access to the repo and executes its build commands |
| Public internet → Vercel production deployment | The deployed static site becomes publicly reachable |

*(No auth, no user input, no persistence in the application itself — ASVS V2/V3/V4/V5/V6 remain not applicable per 01-RESEARCH.md "Security Domain".)*

# Phase 1 — UI Design Contract (REVISED — Revision 2)

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

## Revision Note

**Why this revision exists:** Phase 1 was implemented end-to-end against Revision 1 of this contract (a dark "ink/signal/danger" minimal palette carried forward from the legacy prototype's darkroom/HUD aesthetic). At the Plan 05 human-verification checkpoint, the developer reviewed the live running app and **explicitly stopped the checkpoint rather than approving it**: implementation was technically clean and matched Revision 1's spec correctly, but the resulting UI read as "too dark, minimal, generic, and SaaS/developer-tool-like" — wrong personality for a fun gesture-controlled photobooth puzzle game.

**What changed:** The entire Color and Typography direction is replaced with a bright, warm, playful photography/arcade aesthetic (full rationale and exact tokens below). **What did NOT change:** the seven-route structure, `createBrowserRouter` nested-layout architecture, `AppShell`/`NavBar`/`MobileNavSheet`/`PlaceholderCard` component boundaries, the copywriting contract's actual strings, the spacing scale, the breakpoints, and the shadcn component inventory. Executors should treat this as a **token and visual-treatment swap**, not a rearchitecture.

**Ground truth correction:** Revision 1 stated shadcn was "to be initialized" with preset `style=new-york, dark-mode-default=true`. Since then, Phase 1 execution actually ran `shadcn init`, producing a real `components.json` with `style: "radix-vega"`, `baseColor: "neutral"`, `cssVariables: true` — this revision records the **actual** initialized state (radix-vega, not new-york) rather than the originally-planned one. `index.html` currently hard-codes `<html class="dark">`, which is the direct mechanical cause of the "predominantly black interface" the developer rejected — this revision requires removing that forced class so the new light/cream palette becomes the actual default rendered state.

## Typography

| Role | Size (desktop) | Size (mobile, < 768px) | Weight | Line Height |
|------|-----------------|--------------------------|--------|-------------|
| Body | 16px | 16px | 400 (regular, Inter) | 1.6 |
| Label | 13px | 13px | 400 (regular, IBM Plex Mono, uppercase, `letter-spacing: 0.08em`) | 1.4 |
| Heading | 30px | 22px | 700 (bold, Space Grotesk) | 1.15 |
| Display | 60px | 36px | 700 (bold, Space Grotesk) | 1.05 |

**What changed from Revision 1:** Heading/Display move from Inter 600 to **Space Grotesk 700**. Space Grotesk is a geometric sans with distinct, slightly quirky proportions (squared terminals, tall x-height) — it reads as "designed brand with personality" rather than "default UI framework font," which is exactly the generic-SaaS problem the developer flagged, while remaining clean and legible (not a novelty/display-only face). Body stays on Inter for maximum readability at small sizes. Label stays on IBM Plex Mono — this is a deliberate **keep**, not an oversight: the mono, uppercase, letter-spaced treatment is the one typographic thread tying the new bright UI back to the prototype's camera-HUD/EXIF-readout heritage (used for nav labels, badges, timestamps), which is exactly the "make the camera concept visible in the visual language" requirement applied to type.

Exactly 2 weights declared (400, 700) — do not introduce 500/600 anywhere in this phase. (Weight moved from {400,600} to {400,700} vs Revision 1 — bolder Display/Heading weight better suits the punchier, more playful direction.)

`@fontsource` packages to add/swap: `@fontsource/space-grotesk` (weight 700 only), keep `@fontsource/inter` (weight 400 only — the 600 import can be dropped since Inter no longer carries Heading/Display), keep `@fontsource/ibm-plex-mono` (weight 400 only, unchanged).

## Color

**This is the core of the revision.** Full palette swap from Revision 1's dark-ink-dominant scheme to a warm, bright, photography/arcade-inspired scheme. 60/30/10 discipline is preserved — "tasteful palette including coral, pink, blue, purple, lime/yellow" is satisfied via one **functional accent** (Coral, inside the 10% budget, reserved for interactive elements) plus a capped **Decorative Motif Palette** (pink/blue/purple/lime, explicitly non-interactive, bounded usage) layered on top — see the Visual Motif section below for the reasoning on why these are kept separate from the functional 10% accent.

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `#FFF8EF` ("Cream" — warm off-white, photo-paper toned) | App/page background for every route, the base surface everything else sits on top of |
| Secondary (30%) | `#FFFFFF` ("Paper White", card surfaces) **+** `#1D1626` ("Aperture Ink", nav bar + footer only) | Paper White: placeholder-page content cards, results/gallery/profile stub panels — the "photo tray" surface family, unchanged concept from Revision 1. Aperture Ink: `NavBar` and footer background only — a deliberately small, contained dark surface (not the whole page) that keeps the darkroom/viewfinder callback without making the interface read as "predominantly black" |
| Accent (10%) | `#FF5A47` ("Shutter Coral") | See reserved-for list below — never used generically |
| Destructive | `#C81E3A` ("Ruby") | Destructive actions and error states only — deliberately more magenta-red than Coral so the two are never visually confusable in a UI where Coral is everywhere |

Accent (`#FF5A47` Shutter Coral) reserved for:
- The single primary CTA button per screen (e.g. "Start Playing" on the landing/home page) — button text uses Aperture Ink (`#1D1626`), not white, on the Coral fill (contrast ratio ~6:1, passes AA; white-on-coral would fail AA for normal text at ~2.8:1)
- Active nav-link indicator (2px underline/bottom-border on the current route, shown against the Aperture Ink nav bar)
- Focus-visible outline ring on interactive elements
- "Live" status indicators inherited from the prototype pattern (e.g. a future recording dot) — not used in Phase 1's static placeholder pages, but the token is reserved for this purpose so later phases don't redefine it
- Do NOT use accent for: body links, secondary/ghost buttons, decorative icons/blobs (those use the Decorative Motif Palette below), or general hover states on non-CTA elements

Destructive (`#C81E3A` Ruby) reserved for:
- Error/404 page accent and error banners
- Future destructive confirmations (delete photo in Phase 6, revoke share link in Phase 8) — token reserved now for consistency, not used against live functionality in Phase 1 since no destructive actions exist yet

Supporting neutrals (not part of the 60/30/10 split, but needed for text/dividers on the new light-dominant base):
| Token | Value | Usage |
|-------|-------|-------|
| Ink (primary text) | `#1D1626` | Default body/heading text color on Cream and Paper White surfaces (same hex as Aperture Ink — one dark token doing double duty as both the nav surface color and the default text color, which is what keeps the palette disciplined instead of sprawling) |
| Ink-muted | `#5B5548` | Secondary/muted text on Cream or Paper White (e.g. placeholder body copy, captions) — verified ≥4.5:1 contrast against both `#FFF8EF` and `#FFFFFF` |
| Card border | `#F0E4D3` | Default 1-1.5px border on Paper White cards against the Cream page background (subtle warm line, not the previous cool `#e3e0d8`) |
| Cream text (on dark) | `#FFF8EF` | Text/icons on the Aperture Ink nav bar and footer |

### Decorative Motif Palette (non-interactive, capped, satisfies "coral, pink, blue, purple, lime/yellow")

These four colors exist **only** for decorative/illustrative surface area — background gradient blobs, halftone-adjacent shapes, camera-aperture ring strokes, puzzle-piece silhouettes, corner-bracket framing marks, and small non-primary badges. They are never used for body text, never used for a second competing CTA, and never fill more than a small decorative shape at a time (no full-section color blocks). Combined, their total on-screen visual weight per page should stay well under the Coral accent's footprint — think "confetti," not "competing brand colors."

| Name | Value | Reserved for |
|------|-------|---------------|
| Flash Pink | `#FF3D9A` | Decorative gradient blob partner (paired with Darkroom Violet) behind hero content; puzzle-piece silhouette accents; secondary/non-primary badge fill (Phase 7+, reserved now) |
| Viewfinder Blue | `#2F80ED` | Camera-aperture ring stroke graphics; corner-bracket framing marks (the visual nod to the two-hand index-finger framing gesture); icon tints on the dark nav bar for non-active states |
| Darkroom Violet | `#8B5CF6` | Decorative gradient blob partner (paired with Flash Pink); focus-adjacent illustration accents; subtle card-hover shadow tint (see Component Styling Approach) |
| Flash Lime | `#D6F24C` | Highest-contrast decorative pop — countdown/flash micro-interaction accents, "new" tags, sparkle/spark icon accents. Used most sparingly of the four (this color is closest to the prototype's actual camera-flash white-pop moment) |

**Hard rule for the Decorative Motif Palette:** any time one of these four colors is used as a solid fill large enough to contain text or an icon, pair it with Ink (`#1D1626`) foreground — never white/cream — because Pink, Blue, and Lime especially do not reliably clear 4.5:1 against white at typical fill sizes. This single rule keeps every decorative-color usage accessible by construction without needing a per-instance contrast check.

## Visual Motif: Making the Camera/Photobooth/Puzzle Concept Visible

This section is new in this revision — it did not exist in Revision 1 and is the direct answer to "make the camera/photobooth/puzzle concept visible in the visual language."

1. **Viewfinder corner brackets** — four small L-shaped bracket marks (in Viewfinder Blue or Ink, 2px stroke) positioned at the corners of the hero content area on `/`, echoing the two-hand index-finger framing rectangle that is the actual GAME-02 capture gesture. This is the single most direct visual callback to core gameplay and should appear on the landing hero at minimum.
2. **Camera-aperture ring graphic** — a large, low-opacity (10-15%) concentric-circle SVG graphic (Darkroom Violet or Ink stroke) placed behind the hero headline, suggesting an aperture iris opening — decorative, not literal.
3. **Halftone/dot-grid texture** — a subtle (4-6% opacity) dot-grid pattern across the Cream hero background, evoking printed-photo halftone texture. CSS `radial-gradient` repeating pattern is sufficient; no image asset required.
4. **Soft gradient blobs** — 2-3 large, heavily blurred (`blur-3xl` equivalent, ~24-40% opacity) color blobs using Flash Pink + Darkroom Violet + Viewfinder Blue positioned behind hero content for depth, never behind body text (contrast risk).
5. **Tilted polaroid/photo-strip decorative stack** — a small cluster of 2-3 rotated (−4° to +6°), stacked white rectangle "photo" placeholders near the bottom of the hero or in a feature-highlight area, directly foreshadowing the photo-strip gallery output (GAME-07) users will eventually produce.
6. **Puzzle-grid motif** — a subtle 3×3 grid outline (matching the actual `GRID` constant from the legacy engine) used as a decorative background element or icon accent near any puzzle-related copy, e.g. behind the `/game` `PlaceholderCard` or as a small `Grid3x3` lucide icon tinted Flash Pink.
7. **Shutter-click micro-interaction** — primary CTA buttons scale to `1.03` and gain a soft Coral-tinted shadow bloom on hover/focus (150-200ms ease), and compress to `0.97` on active/press — modeled after the tactile feel of pressing a camera shutter button, not a generic button hover.

None of the above are literal photo/camera imagery requiring new image assets — all are achievable with CSS gradients, SVG strokes, and existing `lucide-react` icons, so this revision introduces no new asset-pipeline dependency.

## Component Styling Approach

- **Buttons:** `rounded-2xl` (not full pill — pill shapes read closer to "childish app," a rounded-but-structured corner reads as "polished, modern, playful"). Primary: Coral fill, Ink text, Coral-tinted shadow on hover (`shadow-lg shadow-[#FF5A47]/25`), scale 1.03 hover / 0.97 active, 150-200ms transition. Secondary/ghost: transparent or Paper White fill, 1.5px Ink border, no shadow, same scale-on-press feedback for consistency.
- **Cards (`PlaceholderCard` and future content cards):** Paper White surface, `rounded-2xl` (20px), 1-1.5px Card Border (`#F0E4D3`), soft ambient shadow with a faint Darkroom Violet or Flash Pink tint at low opacity rather than pure gray/black shadow (`shadow-xl shadow-[#8B5CF6]/10`). On hover: lift (`-translate-y-1`) plus a very slight rotate (`rotate-[-1deg]` or `rotate-[1deg]`, alternating or randomized per card) — evokes physically handling a printed photo. Each stub page's card may optionally carry one small `lucide-react` icon tinted with exactly one Decorative Motif color relevant to its route (e.g. `GalleryHorizontal` in Flash Pink for `/gallery`, `Grid3x3` in Viewfinder Blue for `/game`) — optional polish, not required for MVP completeness, but encouraged so the six stub pages don't feel visually identical/flat.
- **Nav bar:** unchanged structural pattern from Revision 1 (persistent top nav, `h-16`, Aperture Ink background, wordmark left, links right ≥768px, hamburger + `Sheet` below 768px) — only the token values change (Aperture Ink instead of the old pure `#0a0a08`, Coral instead of the old Signal yellow for the active-route underline and focus rings).
- **Footer:** unchanged structural pattern (minimal centered line, Label style, reduced opacity) on the same Aperture Ink surface as the nav bar, for visual bookending of the page.

## Landing Page Treatment

The `/` route gets the most decorative investment, per the developer's explicit note that "the landing page should feel exciting before the user clicks Start Playing." Composition, top to bottom:

1. Cream background with halftone dot-grid texture (item 3 above) and 2-3 blurred gradient blobs (item 4 above) positioned behind the hero, never behind text.
2. Camera-aperture ring graphic (item 2) centered behind the headline at low opacity.
3. Viewfinder corner brackets (item 1) framing the headline + CTA block.
4. `Display` headline, `Body` subhead paragraph, single primary CTA button ("Start Playing," Coral fill, Ink text, shutter-click micro-interaction) linking to `/game` — copy strings unchanged from the Copywriting Contract below.
5. Below the fold or adjacent to the CTA: the tilted polaroid/photo-strip decorative stack (item 5), foreshadowing the photo-strip output feature.

This treatment is achievable entirely within `HomePage.tsx` using Tailwind utilities + inline SVG/CSS gradients — no new asset pipeline, no new dependency beyond the font swap already listed.

## Layout & Breakpoints

Unchanged from Revision 1 — Tailwind v4 default breakpoints, used as-is:

| Breakpoint | Width | Behavior |
|------------|-------|----------|
| Mobile (default) | < 640px | Single-column stack, nav collapses to hamburger → Sheet drawer |
| `sm` | ≥ 640px | Same as mobile, wider gutters |
| `md` | ≥ 768px | Nav bar expands to full horizontal link row; `Display`/`Heading` sizes step up |
| `lg` | ≥ 1024px | Max content width `1200px`, centered; multi-column placeholder grids (e.g. gallery placeholder grid) |

**Navigation pattern:** persistent top nav bar, Aperture Ink background, full-width, `h-16` (64px) tall. Left: mono uppercase wordmark "PINCHPOP" in `Label` style, Coral-colored (was Signal yellow in Revision 1). Right (≥768px): horizontal nav links (Home, Play, Gallery, Profile) in `Label` style, active route gets a 2px Coral bottom border. Below 768px: wordmark stays left, a 44×44px hamburger icon-button replaces the link row and opens a right-side `Sheet` drawer with the same links stacked vertically. The hamburger button carries `aria-label="Open navigation menu"` (icon-only control, no visible text) — unchanged accessibility requirement.

**Footer:** minimal single line, centered, `Label` style at reduced opacity (`~30%`) on Aperture Ink background.

**Page shell:** every route renders inside the shared `<AppShell>` (nav + `<Outlet />` + footer) — unchanged component boundary. Placeholder pages are vertically centered content blocks on the Cream background, using Paper White cards for any content that needs to read as a discrete surface.

## Implementation Notes (revision-specific)

Since `components.json` and all six shadcn primitives already exist in the repo, this revision is a **token + treatment pass**, not a re-init. Concrete steps for the executor:

1. Remove `class="dark"` from `<html>` in `index.html` — light mode becomes the actual default rendered state. The existing `.dark` block in `src/index.css` may be left in place as a dormant future dark-mode variant (no toggle UI is required by this phase), but must not be the active default.
2. Replace the `:root` block in `src/index.css` with the new Color table values above (Cream `#FFF8EF` background, Ink `#1D1626` foreground, Coral `#FF5A47` primary, Ruby `#C81E3A` destructive, Paper White `#FFFFFF` card, `#F0E4D3` border) — same CSS-variable structure shadcn already generated, values only change.

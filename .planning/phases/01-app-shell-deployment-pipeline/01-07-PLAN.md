Prove DEPLOY-01 and DEPLOY-02 against the live production deployment: the app is publicly reachable,
and client-side routes survive direct navigation and hard refresh instead of 404ing.

  <action>
    Export the production URL from `01-06-SUMMARY.md` as `PINCHPOP_DEPLOY_URL` with no trailing
    slash, then run HTTP checks against it. Note that the SPA resolves routes client-side, so the
    HTML body is byte-identical for every route — the assertions below are about status codes,
    content type, and the presence of a real Vite build, not about per-route markup. Per-route
    rendering is confirmed by the human checkpoint in Task 2.

    Check DEPLOY-01: `curl -sS -o /dev/null -w "%{http_code}"` against the root URL must return
    `200`, and the response must be served over HTTPS.

    Check DEPLOY-02: request each of `/game`, `/results`, `/gallery`, `/profile`,
    `/share/deploy-check`, and a deliberately unmatched path such as `/definitely-not-a-route`
    directly (a cold request with no prior in-app navigation — this is what a refresh or a pasted link
    does). Every one must return `200` with a `content-type` of `text/html`, and every response body
    must contain the `div` element with id `root` plus a hashed `/assets/` script reference. A `404`
    on any of these means the rewrite is not in effect in production — the exact silent failure
    Pitfall 2 describes. A `200` that returns Vercel's own error page rather than the app is the same
    failure wearing a different status code, which is why the body assertion is not optional.

    `/share/deploy-check` and `/definitely-not-a-route` are the two most important requests here:
    the first proves a dynamic segment survives a cold load, the second proves the `*` route renders
    the app's own 404 page rather than Vercel's platform 404 (D-03).

    Check that the rewrite does not shadow static assets: request `/vite.svg` and confirm it returns
    `200` with a non-HTML content type. Vercel matches static files before applying rewrites, so an
    HTML content type here would indicate the catch-all is over-matching.

    Record the URL and the status code for every path checked in the plan summary as the DEPLOY-01 /
    DEPLOY-02 evidence trail.

    Do not modify `vercel.json`, the router, or any source file in this task. If a check fails, stop
    and report the failing path and status — the fix belongs in the plan that owns the offending file
    (01-03 for `vercel.json`, 01-05 for the router), not here.
  </action>

## Follow-up pass: camera photo quality fix
- User reported low photo quality after testing camera mode live. Root-caused to three compounding app-level settings, not the webcam hardware:
  1. The shutter could arm on a tiny hand-framed box (`MIN_FRAME_SIZE` was 40px) — the frame becomes the photo's actual resolution at capture with no upscaling, so a small frame made a small, blocky photo. Raised to 260px (`src/lib/camera/engine.ts`), gating both the two-hand pinch auto-arm and the manual "Snap now" button.
  2. `getUserMedia` requested 1280x720 (`src/lib/camera/media.ts`); raised the ideal request to 1920x1080 (best-effort, falls back gracefully on weaker webcams) so a well-framed shot has more real pixels to start from.
  3. Every canvas draw in the capture/export pipeline (`src/lib/camera/effects.ts`, `src/lib/export.ts`) was scaling images without setting `imageSmoothingQuality`, which defaults to a blurrier/blockier "low" in most browsers — added a shared high-quality-context helper in each file so every resize (capture crop, puzzle piece slicing, saved-photo downscale, and the polaroid/photo-strip export upscale) uses `"high"`. Also retuned `effects.ts` constants to match the higher source resolution: film-grain noise `NOISE_STD` 15→7 (was reading as compression noise on the old lower-res source), saved-photo cap `SAVED_MAX_SIDE` 720→1080, JPEG quality 0.82→0.9 (named `SAVED_JPEG_QUALITY`).
- Also added `design-exploration/` to `.gitignore` (untracked local folder, not part of the shipped app).
- Verified: prettier, typecheck, lint, all 20 Vitest tests, and build all exit clean. Did not re-run a full headless-Chrome camera regression for this pass (low-risk constant/smoothing-only changes, no gesture-detection logic changed) — recommend the user re-check camera mode live since they already have a working setup to compare against.

## Security review (user-triggered, `/security-review`) — one real finding, fixed
- User asked whether the site is secure and referenced a "Claude security plugin" from a short-form video — clarified that's just the built-in `/security-review` skill, already available, and ran it for real instead of guessing. Since the whole session had already been committed straight to `main` with no divergent branch, the skill's usual PR-diff review had nothing to diff against — reviewed the session's accumulated Supabase-facing code directly instead (RLS policies across all 5 migrations, the `delete_own_account` RPC, both Storage upload paths, all free-text fields rendered via React).
- **One real, fixed finding** — `src/lib/avatar.ts`: `uploadAvatar()` accepted any file whose `file.type` started with `"image/"`, which admits `image/svg+xml`, then uploaded it to the **public** `avatars` bucket using that attacker-controlled value as the stored `Content-Type`. Supabase Storage serves files by their stored Content-Type, not their filename extension, so an uploaded SVG with an embedded `<script>` would execute if its public URL were opened directly (not via an `<img>` tag) — a real stored-XSS pattern, not a theoretical one, since picking any real `.svg` file already reports that exact MIME type with zero tampering needed. Comparative analysis against the rest of the codebase made this stand out: the project's *existing* user-image-upload path (`capturePhotoFromImage` in `effects.ts`, from the "upload a photo" camera feature) already re-encodes everything through a `<canvas>`, which rasterizes away any embedded script regardless of input type — the new avatar path didn't follow that established, already-safe pattern.
- **Fix**: replaced the prefix check with an explicit allowlist (`image/jpeg`/`image/png`/`image/webp` only); the stored `Content-Type` is now only ever one of those three validated values, never the raw client-supplied one. Also tightened the `<input accept>` attribute on `AccountPage.tsx`'s file picker to match (a UX nicety — the real boundary is in `avatar.ts`, not the picker).
- **Bonus bug caught while fixing it** (not a security issue, a correctness one): `deleteAccount()` only ever cleared the `photos` Storage bucket before calling the delete RPC. Since Supabase refuses to delete a user who still owns *any* Storage object in *any* bucket, anyone who'd uploaded an avatar would have had "Delete account" silently fail with an opaque Postgres error. Fixed by clearing both `photos` and `avatars` before the RPC call, via a small shared helper rather than duplicating the list-then-remove logic twice.
